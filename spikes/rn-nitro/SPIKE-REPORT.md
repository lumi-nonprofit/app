# Spike #1b — GO/NO-GO report: RN ↔ Rust binding via **Nitro** (ADR 0003 gate)

**Date:** 2026-06-14 · **Verdict: GO.** A live JS→Rust→JS round-trip ran on **real
arm64 hardware** (Pixel 8a, GrapheneOS) with §1 intact. This clears the spike #1b gate in
ADR 0003 and **empirically validates the v1 binding choice** — React Native, bound to the
shared Rust core, with **Nitro** as the binding mechanism (adopted after
create-react-native-library 0.49 dropped its C++ TurboModule template; ADR 0003's
accessibility / UI-preservation reasoning is unchanged).

**Validated stack (end-to-end, at runtime):**

```
React Native (New Arch / Fabric)
  → Nitro Modules
    → C++ HybridObject  (HybridLumiCrypto)
      → Rust C ABI       (lumi-ffi-cabi: x25519 + ChaCha20-Poly1305 + HKDF + SECRETS registry)
```

This is the inverse of spike #1 (`spikes/rn-ffi/SPIKE-REPORT.md`, ubrn → NO-GO): there the
binder's live round-trip never ran; here it does, on a real device, through hand-owned C++
whose JSI glue is **statically generated by Nitrogen** (so the bus-factor-1 hand-glue risk
ADR 0003 flagged is retired — we own the method bodies, not the marshalling).

## Environment honesty

This spike was **run by Anna on her own machine** (Fedora 44 + Pixel 8a over USB), not in
this sandbox — the sandbox has no C compiler, NDK, or device. The kit under
`spikes/rn-nitro/` was populated by hand into a throwaway scaffold at `~/lumi-crypto-spike`
(create-react-native-library 0.49.10, `--type nitro-module`). The result below is her
on-device run; the three fixes were applied live during it.

## Run method (honest)

GO was reached via the **DEBUG APK on the dev-loop** (Metro + `react-native run-android
--no-packager`), **not** the offline release APK. `assembleRelease` **compiled the native
code cleanly for both arm64-v8a and x86_64** but failed downstream at **Java dex-merge**
(see deferred item 1). So: **the native binding compiles clean in both debug and release;
only release Java packaging is unresolved** — a create-react-native-library packaging
issue, not a binding-mechanism issue.

**Scope actually exercised vs. the gate as written:** the gate (RUNBOOK / ADR 0003)
asked for the round-trip on the **x86_64 emulator AND the arm64 Pixel**. The **arm64
Pixel leg ran live and passed**; the **x86_64 emulator leg was not run** (optional
cross-arch confirmation — x86_64 nonetheless compiled fine in the release CMake). The
earlier ADR 0003 gate text also named a **4-ABI** Android build; that was narrowed **by
design** (RUNBOOK Step 7 restricts `reactNativeArchitectures` to `arm64-v8a,x86_64`) to
the **2 ABIs** we run — arm64-v8a (built + run) + x86_64 (built only); armeabi-v7a/x86
were out of scope. iOS remains deferred per ADR 0001 (no Mac; Android-first). So — like
iOS — the x86_64-runtime and full-4-ABI clauses are satisfied by **narrowed scope, not
executed as literally written**; the verdict is GO on the strength of the live
arm64-device round-trip plus the clean x86_64 build.

## Three issues hit and fixed (during the run)

Recorded against the runbook steps so a re-run is clean (also annotated in `RUNBOOK.md`):

1. **Step 5 — Rust std targets not actually installed.** `build-rust-android.sh` failed
   with `error[E0463]: can't find crate for core` for `aarch64-linux-android` — an earlier
   `rustup target add` hadn't stuck, and the `rustup` toolchain at `~/.cargo/bin` shadows a
   system dnf `rust`. **Fix:** `rustup target add aarch64-linux-android x86_64-linux-android`,
   then re-run the script.
2. **Step 8 — autolinked Java package path mismatch.** First `assembleDebug` failed at
   `:app:compileDebugJavaWithJavac`: RN autolinking generated `PackageList.java` importing
   `com.margelo.nitro.lumicrypto.LumiCryptoPackage`, but cra-library generated the class at
   `com.lumicrypto.LumiCryptoPackage`. With no `react-native.config.js`, autolinking
   auto-derives the import from the Nitro namespace, which disagreed with the scaffold.
   **Fix:** move `android/src/main/java/com/lumicrypto/LumiCryptoPackage.kt` →
   `android/src/main/java/com/margelo/nitro/lumicrypto/LumiCryptoPackage.kt` and set its
   `package` to `com.margelo.nitro.lumicrypto`. (That class is a no-op `TurboReactPackage`
   whose real job is `System.loadLibrary("lumicrypto")` in its init block → fires
   Nitrogen's `OnLoad` → registers the C++ HybridObject; it must exist **and** be findable
   at the autolinked path.)
3. **Step 8 — duplicate class from an unused template dep.** Next `assembleDebug` failed at
   `:app:mergeLibDexDebug`: `com.facebook.react.viewmanagers.RNCSafeAreaProviderManagerDelegate`
   defined twice, from `react-native-safe-area-context` — an example-template dep declared
   only in `example/package.json` and never imported by the harness. **Fix:**
   `cd example && yarn remove react-native-safe-area-context`.

## Production hygiene — deferred follow-ups (NOT spike blockers)

These were stepped around for the spike (debug dev-loop) and belong to the real app build:

1. **Release-APK dex collisions.** `assembleRelease` fails at `:app:mergeDexRelease` with
   `com.facebook.fbreact.specs.NativeAccessibilityInfoSpec` (and generally the
   `com.facebook.fbreact.specs` / `com.facebook.react.viewmanagers` set) **defined twice** —
   the library module bundles RN-core codegen specs that the app's own copy of React Native
   already provides. A known create-react-native-library + New-Architecture packaging
   interaction. **Fix direction (real app):** stop the library module from
   bundling/regenerating the core (and third-party) codegen specs the app already ships.
2. **16 KB ELF page alignment.** Debug-build advisory ("This app isn't 16 KB-compatible.
   ELF alignment check failed"). Our own `liblumicrypto.so` reported `LOAD segment not
aligned` → **fix with the linker flag `-Wl,-z,max-page-size=16384`** (or NDK r28+, which
   defaults to 16 KB-aligned output). Other flagged libs (`libreactnative`, `libhermes`,
   `libjsi`, `libfbjni`, `libc++_shared`, the Fresco image libs, `libNitroModules`) are
   prebuilt deps → resolved via 16 KB-aligned upstream versions. **Required for Google Play
   for Android-15+ targets;** irrelevant to the spike.

empirically validated on real arm64 hardware with §1 intact. Proceed to real RN↔core
integration (M1+) on this stack, after Anna's review. The two deferred items above are
production-build hygiene to carry into the real app, not blockers.
